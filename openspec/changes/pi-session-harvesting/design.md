## Context

nano-brain harvests AI coding-agent sessions into its document store so `memory_query`/`memory_wake_up` can recall past work across sessions. Two sources exist today:

- **Claude Code**: `ClaudeCodeHarvester` (`internal/harvest/claudecode.go`) scans `~/.claude/projects/<encoded-cwd>/*.jsonl`, one file per session.
- **OpenCode**: `OpenCodeSQLiteHarvester` (`internal/harvest/opencode_sqlite.go`) reads a SQLite DB.

Both are wired at daemon startup (`cmd/nano-brain/main.go`) via a per-source `init*Harvesters()` function that lists registered workspaces, matches each to that source's on-disk layout, and instantiates one harvester per match. Both register with a shared `Runner` (`internal/harvest/runner.go`) that ticks all harvesters on one interval.

A third agent, **Pi**, is confirmed present on this machine at `~/.pi/agent/`, with its own per-project session log format. The schema below was corrected during the mandatory two-reviewer adversarial pass (see "Review outcome" below) after both reviewers independently checked it against all 120 real session files on this machine (7,839 total lines) rather than the 2-3 files this draft originally sampled — the corrected version below is what implementation must follow:

- **Session location:** `~/.pi/agent/sessions/<encoded-cwd>/<ISO8601-timestamp>_<uuid>.jsonl` — one directory per project, one file per session. Example: `~/.pi/agent/sessions/--Users-tamlh-workspaces-self-AI-Tools-nano-brain--/2026-08-07T08-22-38-048Z_019fdb51-2ce0-7085-a1d1-471be7c19602.jsonl`.
- **Directory naming:** the project's absolute path with its leading `/` stripped, every remaining `/` replaced by `-`, then wrapped in a leading and trailing `--` (e.g. `/Users/tamlh/workspaces/self/AI/Tools/nano-brain` → `--Users-tamlh-workspaces-self-AI-Tools-nano-brain--`). This is Pi's own scheme, distinct from Claude Code's (`encodeClaudeProjectsDir`, which replaces the leading `/` too and does *not* wrap in `--`, producing `-Users-...` instead).
- **File format (JSONL, one JSON object per line) — corrected schema:**
  - Line 1 — session header: `{"type":"session","version":3,"id":"<uuid>","timestamp":"<ISO8601>","cwd":"<absolute project path>"}`. `id` is the session identity; `cwd` is ground truth for workspace matching (stronger than trusting the directory encoding alone).
  - Subsequent lines — events: `{"type":"model_change"|"thinking_level_change"|"message","id":"<hex>","parentId":"<hex-or-null>","timestamp":...}`. **The top-level `type` for a content-bearing event is always the literal string `"message"`** — role differentiation lives in the *nested* `message.role` field, not at the top level. Verified role distribution across all 120 real files: `toolResult: 3710, assistant: 3370, user: 325` — **`toolResult` is its own top-level role and is the single largest category**, not a sub-part of `assistant` content the way Claude Code nests tool results inside an assistant message.
  - `message.content` is an array of typed blocks. Verified block-type distribution: `text: 5869, toolCall: 3717, thinking: 2004, image: 9`. A parser that only handles `{"type":"text","text":...}` (as originally drafted here) silently drops roughly half of real transcript content — every `toolCall`, every `thinking` trace, and any `image` block.
  - `model_change`/`thinking_level_change` lines remain metadata-only and are still skipped for rendering (see Decision 3).
  - Lines chain via `parentId` (each event's `id` becomes the next event's `parentId`), analogous to Claude Code's `parentUuid` chain — no branching was observed across all 120 real session files (both reviewers independently re-checked this against the full set, not just the original sample), so v1 assumes a linear chain matching file order (see Non-Goals).

A related but distinct directory, `<repo>/.pi-subagents/artifacts/`, holds Pi's *subagent delegation* records (one `meta.json` + `input.md` + `output.md` + `transcript.jsonl` quadruplet per delegated subagent run, e.g. a code-review subagent). It is project-relative (inside the repo being worked on), not global like `~/.pi/agent/sessions/`, and represents a different kind of artifact (a delegated review run, not the primary coding session). This proposal does not harvest it — see Non-Goals.

## Goals / Non-Goals

**Goals:**
- Ingest Pi's primary per-project session transcripts into the same document store, collection (`sessions`), and summarization pipeline already used for Claude Code and OpenCode, so `memory_query`/`memory_wake_up` surface Pi work alongside the other two sources.
- Reuse the existing `Harvester` interface and `Runner` unchanged — this is an additive third implementation, not a redesign.
- Default to disabled (opt-in), matching the Claude Code harvester's existing privacy-conscious default.

**Non-Goals:**
- Harvesting `.pi-subagents/artifacts/` (subagent delegation transcripts) — different shape, different directory model, flagged as a candidate follow-up change, not part of this one.
- A generic "coding agent adapter registry" or plugin-discovery mechanism. The `Harvester` interface is already the generalization point; adding a fourth agent later means writing one more file following this same recipe, not extending infrastructure.
- Live fsnotify-based watching of `~/.pi/agent/sessions/`. Matches existing Claude Code/OpenCode `session_dir` behavior: discovery happens once per harvest tick.
- Parsing non-linear (branching) Pi conversation trees. No branching was observed across all 120 real session files on this machine (re-checked by both adversarial reviewers, not just the original sample); if it turns out to exist, the fallback (treat file order as canonical) still produces a readable, if potentially reordered, transcript — not a crash or data loss.
- Rendering `image` content blocks as image data. No OCR, no multimodal embedding, no base64 decoding. An `image` block renders as a single placeholder line (e.g. `[image omitted]`) so document structure is preserved without silently dropping the turn. Only 9 occurrences observed across 120 real files — low-value to solve further for v1.
- Auto-expanding `~` in `harvester.pi.session_dir`. `ClaudeCodeHarvesterConfig.SessionDir` has no tilde-expansion today (verified: `initClaudeCodeHarvesters` calls `os.Stat` on the raw configured string; the repo's only tilde helper, `expandTildeForConfig`, is wired solely to `Summarization.OutputDir`). Pi's config field matches that exact precedent: no default value, no auto-expansion, operator sets an absolute path explicitly. Docs suggest `~/.pi/agent/sessions` as the value to set, but nothing in code resolves `~` for it — introducing new tilde-resolution code for one config field, untested anywhere else in the harvester config surface, is out of scope for this change.
- Propagating `TicketPatterns` onto `PiHarvesterConfig`. `ClaudeCodeHarvesterConfig.TicketPatterns` and `OpenCodeHarvesterConfig`'s equivalent are dead configuration today — read by no production code (their only would-be consumers, `NewEngine`/`NewEngineWithTicketPatterns`, have zero call sites). `PiHarvesterConfig` omits this field entirely rather than copying a third orphaned config knob with no defined behavior.

## Decisions

**Decision 1 — Model `PiHarvester` directly on `ClaudeCodeHarvester`, not `OpenCodeSQLiteHarvester`.**
Both Claude Code and Pi are "one JSONL file per session, in a per-project directory" — the same shape. OpenCode's SQLite-DB shape is unrelated. Copying the Claude Code harvester's structure (directory scan → per-file parse → render → hash → enqueue) minimizes new code and keeps the two most-similar harvesters easy to compare/maintain side by side.
*Alternative considered:* a single generic "JSONL directory harvester" parameterized by a format-specific parse function, shared by Claude Code and Pi. Rejected for this change: Claude Code's parser has accumulated real-world edge-case handling (documented dedup/timeout/injection-parser fixes per recent commit history) that would need careful, separately-reviewed extraction to avoid regressing it. Given only two data points (Claude Code, Pi) so far, extracting a shared abstraction now is premature per this repo's own YAGNI guidance; revisit if a third JSONL-shaped source appears.

**Decision 2 — Match workspace→directory by re-encoding the workspace path with Pi's scheme, not by decoding the directory name.**
This mirrors `encodeClaudeProjectsDir`'s established, already-accepted precedent: the encoding (`/` → `-`, wrapped in `--`) is not injective — a workspace path containing a literal `-` can theoretically collide with another path's encoding. `encodeClaudeProjectsDir`'s own doc comment accepts this exact risk for Claude Code ("silent miss... benign, no crash"). The same trade-off is accepted here for consistency and because the alternative (writing a decoder and validating it against the `cwd` field inside each session's header line) adds parsing complexity for a collision that, per the existing precedent, is deemed acceptable to leave as a silent miss.
*Mitigation available if this proves insufficient later:* the header line's `cwd` field is ground truth and could be used to double-check a directory match, or even to walk all directories under `~/.pi/agent/sessions/` and match by `cwd` instead of by name — deferred as a follow-up, not implemented in v1, to keep the initial change small and directly comparable to the Claude Code precedent.

**Decision 3 — Ignore `model_change`/`thinking_level_change` events; render every `type:"message"` line, including the `toolResult` role and non-text content blocks.**
`model_change`/`thinking_level_change` carry provider/model bookkeeping, not conversation content, and are skipped for rendering — matching how Claude Code's harvester already ignores non-content JSONL line types. Within `type:"message"` lines, rendering dispatches on the *nested* `message.role` (`user`/`assistant`/`toolResult`) — all three are rendered, not just `user`/`assistant` — and on each content block's `type`: `text` renders as-is; `toolCall` renders as a compact "tool call" line (name + arguments); `thinking` renders as a labeled thinking-trace block; `image` renders as a placeholder (see Non-Goals). This replaces the original draft's assumption that only `{"type":"text","text":...}` blocks exist — verified false against all 120 real session files (`toolResult` is the single largest role at 3710 occurrences; `toolCall`/`thinking`/`image` are 3717/2004/9 respectively).

**Decision 4 — `SourcePi` gets an explicit `buildSourcePath` case, not just the generic fallback.**
`buildSourcePath`'s existing default case already produces the correct `summary://pi/<id>` shape for any unrecognized source string — so this is not functionally required. It's added anyway (one line) because the function's own comment states each *known* source gets an explicit case, and Pi becomes known the moment this change ships. (Verified by both adversarial reviewers: byte-identical output to the default fallback, zero divergence risk — this one stays exactly as originally drafted.)

**Decision 5 — Pi's renderer emits Claude-Code-style markdown conventions, and `pipeline.go`'s strip-function switch gets an explicit `case SourcePi: stripped = StripClaude(...)`.**
Found during adversarial review: `internal/summarize/pipeline.go`'s `Source` switch has exactly two cases, `SourceClaude` → `StripClaude` and `default` → `StripOpenCode`. A `SourcePi` value falls into `default` today, so a Pi transcript — rendered in Claude-like markdown per Decision 1 — would be run through `StripOpenCode`'s regexes (`replaceToolOutputs`, etc.), which target OpenCode's rendering conventions, not Pi's. This is not a hypothetical: `buildSourcePath`'s "unchanged pipeline" framing in the original proposal draft did not account for this second dispatch site.
*Resolution:* the renderer's job includes normalizing Pi's tool-call/tool-result/thinking blocks into the same markdown conventions `renderClaudeCodeMarkdown` already produces for Claude Code, specifically so `StripClaude` (correctly wired via the new `case SourcePi`) can compact them using its existing regexes unchanged. `pipeline.go` gains one line; no new strip function is written.

**Decision 6 — `sourceFromTags` (`internal/server/handlers/summarize.go`) must also recognize a `"pi"` tag.**
Found during adversarial review, and initially mistaken for a duplicate of Decision 5 until the debate step traced the actual call chain: `sourceFromTags` is a *second*, independent place that classifies a document's source from its tags, used only on the manual/backfill re-summarization path (`TriggerSummarize`), not the fresh-harvest path. It recognizes `"claude_code"`/`"opencode"` and defaults everything else — including a `"pi"` tag — to `"opencode"`. Left unfixed, a manually re-summarized Pi document would look up the wrong dedup path (`summary://opencode/<id>` instead of the real `summary://pi/<id>`), never find its own prior document, and write a second, wrongly-sourced duplicate. This is the same *class* of bug as Decision 5 (a third `Source` value unhandled by a string-matching function) but a genuinely separate fix at a separate call site — patching only `pipeline.go` does not fix this path, and patching only `sourceFromTags` does not fix fresh harvest.
*Resolution:* `sourceFromTags` gains a `"pi"` tag → `"pi"` branch, mirroring its existing `"claude_code"` → `"claude"` branch.

**Decision 7 — Malformed-line handling matches `ClaudeCodeHarvester`'s actual behavior: skip the bad line, keep parsing the rest of the session.**
The original draft specified "one malformed line skips the whole session." Verified against `ClaudeCodeHarvester.parseJSONLFile` (`internal/harvest/claudecode.go:407-419`): it does `continue` on a JSON-unmarshal error for a single line — no log, no error counter, and the session is *not* discarded; every other valid line still renders. Since this proposal's stated goal is modeling Pi "directly on" Claude Code, the harvester-per-line behavior should match exactly rather than introduce a stricter, undocumented deviation. A fully truncated last line (process killed mid-write, no trailing newline, partial JSON) falls under the same per-line-skip rule. **Correction (found in the code-review pass after implementation):** because dedup is presence-based, not content-hash-based (see the corrected "deduplicated by presence" requirement in spec.md), a session harvested while its last line was still mid-write does NOT self-heal on a later tick — once any version is summarized and persisted, the presence check skips all future ticks regardless of new content. This is the same inherited limitation as the "session grows" case, not a truncation-specific gap.

**Decision 8 — Config target is `internal/config/template.go`'s `fullConfigTemplate`, not `config.example.yml`.**
The original draft assumed a `config.example.yml` file exists in this repo (mirroring a common convention). Verified false: no such file exists; the actual mechanism generating the documented full-config reference is `internal/config/template.go`'s `fullConfigTemplate` constant (already has a `claudecode:` block), guarded by `TestRenderConfig_RoundTrip`. The new `pi:` block goes there instead, next to the existing `claudecode:` block.

## Risks / Trade-offs

- **[Risk] Directory-encoding collision (see Decision 2)** → Mitigation: accepted, matching existing Claude Code precedent; silent miss (workspace gets no Pi harvester), never a crash or wrong-workspace ingestion, because a false-positive match would require the *encoded* name to collide, not just the raw path.
- **[Risk] Pi's session-directory tree is large (29 MB across all projects on this machine, growing) and un-fsnotify-watched** → Mitigation: matches existing OpenCode/Claude Code `session_dir` polling behavior already in production; no new resource-usage class introduced. Per-tick cost is bounded by presence-based short-circuiting (a session with an existing document is skipped before its file is re-read past the header line), identical to `ClaudeCodeHarvester`.
- **[Risk] Assumed-linear `parentId` chain (see Non-Goals) turns out wrong for some future Pi session** → Mitigation: worst case is a transcript rendered in file-append order instead of logical parent order; still readable, still hashed/deduped correctly by session `id`. Not a data-loss or crash risk.
- **[Trade-off] Disabled by default** → New installs get zero Pi harvesting until an operator opts in, same friction as Claude Code today. Accepted as consistent, privacy-respecting default; documented in the config keys.
- **[Risk, found + resolved during review] Two independent `Source`-dispatch sites (`pipeline.go`'s strip switch, `sourceFromTags`) both defaulted an unrecognized `"pi"` value to the wrong source** → Mitigation: both fixed explicitly (Decisions 5 and 6); tasks.md requires a regression test for each, plus a note that fixing only one site does not fix the other (they interact only on the manual-resummarize path — see Decision 6).
- **[Risk, found + resolved during review] Original schema draft would have silently dropped ~half of real transcript content** (`toolResult` role, `toolCall`/`thinking`/`image` blocks) → Mitigation: schema corrected (see "Context" above and Decision 3) before any parser code is written.

## Migration Plan

No data migration. Additive: new config keys (default `enabled: false`), new source-code files, one new `buildSourcePath` case, one new `pipeline.go` case, one `sourceFromTags` branch, one new harvester wired at startup. Rollback = revert the commit / set `harvester.pi.enabled: false` (already the default). No goose migration needed — reuses the existing `sessions` collection and `documents`/`chunks` schema.

## Review Outcome

The mandatory two-independent-adversarial-reviewer step (Reviewer A: architecture; Reviewer B: delivery) ran after this draft's initial authoring, followed by a full debate exchange (each reviewer received the other's raw findings and returned `accept`/`rebut`/`amend` verdicts). Result: **15 findings total (3 HIGH, 4 MEDIUM, ~8 LOW/confirmed-fine), zero rebuttals, zero disputed findings** — every HIGH/MEDIUM finding was accepted by both reviewers and is now resolved in this document, proposal.md, tasks.md, and specs/pi-session-harvesting/spec.md. The debate step additionally surfaced that two independently-discovered HIGH findings (the `pipeline.go` strip-dispatch bug and the `sourceFromTags` classification bug) share one root cause — an unhandled third `Source` value — but require two separate fixes at two separate call sites (see Decisions 5-6); this would not have been caught without the cross-reviewer exchange.

Confirmed clean (no action needed): the directory-encoding collision risk (Decision 2, matches accepted Claude Code precedent), no new interaction with the `fix-install-ux-regressions`/`sessions`-logical-collection fix (`isLogicalCollection` gates by collection name, not source — Pi reusing `Collection:"sessions"` is automatically covered), no new PII/secret exposure versus existing Claude Code/OpenCode harvesting (symmetric, pre-existing, not a regression), and `SourcePi`'s explicit `buildSourcePath` case (Decision 4, confirmed functionally inert but harmless).
